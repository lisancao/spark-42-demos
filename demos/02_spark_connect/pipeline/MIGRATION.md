# Migrating the Orders Pipeline to Spark Connect

This document walks through the migration of a small pipeline from Spark Classic to Spark Connect.
`pipeline_before.py` runs on Spark Classic and is submitted with `spark-submit`. `pipeline_after.py`
runs the same pipeline over Spark Connect as an ordinary Python program. The two files differ in one
place for each of the seven migration layers described in §9 of the
[blog post](../blog_spark_connect.md), and both call the transformations in `lib/transforms.py`
unchanged.

The pipeline is small so that it runs in seconds on the cluster in `compose.yaml`. The same layers
applied to a 357-line pipeline copied from the `lakehouse-stack` project are described in the
[case study](../case_study/lakehouse_stack/README.md). Results were recorded on 2026-09-10 against
Apache Spark 4.2.0.

## Running the Migration

From the project root, with the cluster running (`make up`):

```bash
make audit      # report Spark Connect incompatibilities in both files
make pipeline   # run both versions, then compare their output
```

`make pipeline` runs three commands. The Spark Classic version is submitted with `spark-submit`
inside the Connect server's container, against the standalone master. The Spark Connect version runs
on the host. `parity.py` then compares the two outputs. Each run prints the row count of every table
it writes, and the comparison ends the output:

```
parity: /opt/spark/work-dir/out/classic  vs  /opt/spark/work-dir/out/connect
  bronze_events                ok       238 rows, hashes match
  bronze_stores                ok       4 rows, hashes match
  bronze_brands                ok       5 rows, hashes match
  silver_orders_enriched       ok       235 rows, hashes match
  silver_order_lifecycle       ok       55 rows, hashes match
  gold_delivery_performance    ok       4 rows, hashes match
  gold_brand_summary           ok       5 rows, hashes match
  7/7 tables identical
```

## The Pipeline

The input is generated by `input/generate.py` from a fixed seed: 238 order events for 60 orders, of
which 5 are never delivered, plus 3 events without an order ID, 4 stores and 5 brands. Every run
therefore starts from the same data. Table 1 lists what the pipeline writes.

*Table 1. Tables written by the pipeline*

| Table | Built by | Rows |
|---|---|---|
| `bronze_events` | `parse_events()` over `input/order_events.jsonl` | 238 |
| `bronze_stores` | `input/stores.csv` | 4 |
| `bronze_brands` | `input/brands.csv` | 5 |
| `silver_orders_enriched` | `enrich_orders()`: drops events without an order ID, parses the JSON body, adds time columns, joins stores with a broadcast hint, and computes `delivery_km` with a Python UDF | 235 |
| `silver_order_lifecycle` | `order_lifecycle()`: one row per delivered order, with preparation, delivery and total minutes | 55 |
| `gold_delivery_performance` | `delivery_performance()`: averages and percentiles per city | 4 |
| `gold_brand_summary` | `brand_summary()`: orders and revenue per brand | 5 |

The Python UDF imports `lib/geo.py`, which is not installed on the cluster. Making that module
available to the executors is the Layer 4 change.

## Changes by Layer

Table 2 lists the change in each layer, with line numbers in each file. Everything else, including
every call into `lib/transforms.py` and the loop that writes the tables, is identical.

*Table 2. The change in each layer*

| Layer | `pipeline_before.py` | `pipeline_after.py` |
|---|---|---|
| 0. Session creation | lines 20 to 25: `SparkSession.builder` ... `.getOrCreate()` | lines 23 to 33: `build_session()` |
| 1. Pipeline logic | line 30: `events.rdd.isEmpty()` | line 38: `events.isEmpty()` |
| 2. Data sources and catalogs | line 14: an input path next to the file, on the host | line 16: `PIPELINE_INPUT`, by default `/demo/pipeline/input`, a path on the server |
| 3. Configuration | lines 22 and 23: `.config("spark.sql.shuffle.partitions", "8")` and `.enableHiveSupport()` | line 34: `spark.conf.set("spark.sql.shuffle.partitions", "8")` |
| 4. Dependencies | line 27: `spark.sparkContext.addPyFile(...)` | line 35: `spark.addArtifact(..., pyfile=True)` |
| 5. Execution and operations | line 26: `spark.sparkContext.setLogLevel("WARN")`; submitted with `spark-submit` in a container | no log level call; run with `python` on the host |
| 6. Security and identity | no credentials | `make pipeline` adds `user_agent=orders-pipeline` to the connection string |

### Layer 0: Session Creation

`build_session()` is the function shown for Layer 0 in the blog post. When `SPARK_REMOTE` is
set, it returns a Spark Connect session. When `SPARK_API_MODE=connect` is set instead, it sets
`spark.api.mode`. With neither, it returns a Spark Classic session, so the migrated file can still
run the way the original did.

### Layer 1: Pipeline Logic

`DataFrame.rdd` raises `JVM_ATTRIBUTE_NOT_SUPPORTED` under Spark Connect, because an RDD is an object
in the driver JVM. `DataFrame.isEmpty()` answers the same question without an RDD, and it works on
Spark Classic as well.

### Layer 2: Data Sources and Catalogs

Under Spark Connect, the server opens input files, so a path must name a location the server can
read. `pipeline_before.py` derives its input path from its own location, which works when the driver
runs beside the files. The cluster in `compose.yaml` mounts `pipeline/` read-only at
`/demo/pipeline`, and `pipeline_after.py` reads from there. With `PIPELINE_INPUT` set to the host
path instead, the Connect run fails (host path shortened):

```
pyspark.errors.exceptions.connect.AnalysisException: [PATH_NOT_FOUND] Path does not exist:
file:/<project>/pipeline/input/order_events.jsonl. SQLSTATE: 42K03
```

The audit cannot report this layer. A path is a string, and whether it names a location on the
server cannot be determined from the source.

### Layer 3: Configuration

`spark.sql.shuffle.partitions` is a value the server reads when it plans a query, so a client can set
it; `pipeline_after.py` sets it with `spark.conf.set()` once the session exists.
`enableHiveSupport()` is removed. Under Spark Connect it does not raise, but it has no effect:
`spark.sql.catalogImplementation` is a static setting of the server and remains `in-memory`
(blog post §7).

### Layer 4: Dependencies

`distance_udf()` imports `geo` inside the UDF, so the import runs on an executor.
`SparkContext.addPyFile()` is not available under Spark Connect, and `SparkSession.addArtifact()`
with `pyfile=True` ships the file to the session instead. `examples/08_add_artifact.py` shows the
UDF failing with `ModuleNotFoundError: No module named 'geo'` before the call and succeeding after
it.

### Layer 5: Execution and Operations

`setLogLevel()` is reached through `SparkContext`, and the log level belongs to the server's JVM, so
the call is removed and the level is set in the server's log4j2 configuration. Submission changes as
well. The Spark Classic version runs inside a container:

```bash
docker compose exec -T spark-connect /opt/spark/bin/spark-submit \
    --master spark://spark-master:7077 --conf spark.cores.max=1 \
    --conf spark.driver.host=spark-connect \
    /demo/pipeline/pipeline_before.py --output /opt/spark/work-dir/out/classic
```

The Spark Connect version runs on the host:

```bash
SPARK_REMOTE="sc://localhost:15002/;user_agent=orders-pipeline" \
    .venv/bin/python pipeline/pipeline_after.py --output /opt/spark/work-dir/out/connect
```

The output path belongs to Layer 2 as much as to Layer 5: in both runs it is a path on the cluster,
in the volume that the worker and the Connect server share.

### Layer 6: Security and Identity

This pipeline reads local files and holds no credentials, so the only change is that `make pipeline`
adds `user_agent=orders-pipeline` to the connection string (blog post §5). The case study
shows the Layer 6 change for a pipeline whose catalog credentials move from every node to the
Connect server.

## Auditing Both Files

`make audit` runs `tools/compat_audit.py` on both pipeline files and on
`examples/10_eager_and_lazy.py`. Each finding is printed with a message and a fix; the tagged lines
are:

```
pipeline_before.py:26:0 [BLOCKER/L5] setLogLevel()
pipeline_before.py:27:0 [BLOCKER/L4] addPyFile()
pipeline_before.py:30:3 [BLOCKER/L1] .rdd
pipeline_before.py:21:4 [BEHAVIOR/L3] enableHiveSupport()
examples/10_eager_and_lazy.py:25:0 [BEHAVIOR/L1] except AnalysisException around transformations
examples/10_eager_and_lazy.py:38:0 [BEHAVIOR/L1] temp view 't' registered 2 times

6 finding(s): 3 BLOCKER, 3 BEHAVIOR, 0 PERF
```

`pipeline_after.py` has no findings. The `enableHiveSupport()` finding is reported at line 21, where
the builder chain begins. The two findings in example 10 are included to show behavior findings,
which this pipeline does not produce.

## Verifying Parity

`parity.py` compares each table on its schema, its row count and an order-independent content hash.
The row counts alone would miss a table with the right number of rows and
different values. `make pipeline` reported `7/7 tables identical` on four runs, and
`tests/spark/test_parity.py` constructs each difference the comparison must detect.

## Size of the Change

`git diff --no-index --stat pipeline/pipeline_before.py pipeline/pipeline_after.py` reports 21
insertions and 13 deletions, including the module docstrings.
